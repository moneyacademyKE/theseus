# Theseus v1.0 Enhancement Roadmap

**Date:** 2026-09-08 · **Baseline:** v0.9.0 (tag pushed, poller running it) · **Author:** OpenCrabs, at owner request

## Context

The robustness era is closed: durable outbox, graceful shutdown, boot health,
honest verdicts, progress-based stall detection, skills contract, 69 e2e suites
green, R1–R5 hygiene shipped. v1.0 is the **product era**: the chat surface
catches up with the plumbing.

**Verified current state** (`bb stats`, live home):

| Fact | Value |
|---|---|
| Goal workspaces (live home) | 11 — 7 fulfilled, 3 stalled, 1 unresolved |
| Authoring latency (dogfood, reasoning model) | ~44 min, silent |
| Load-bearing skills in dogfood | 1 of 5 cited |
| Artifact delivery to topic | text outcome only |
| Goal ops from chat | `/goal resume` exists; list/status/cancel do not |

**Definition of v1.0 done:** a user posts a goal in a topic, *watches it think*,
receives the built artifact as a file, and can interrogate it with `/goal`
commands — nobody SSHes in. Then `bb release` cuts v1.0.0.

---

## V1 — Time-to-value: kill the 44-minute silence

The dogfood's worst product fact wasn't a bug: authoring worked honestly for 44
minutes while the topic heard nothing. Three separable fixes:

- **V1.1 Author-progress message.** One message in the owning topic, edited in
  place as authoring rounds complete ("authoring… round 7 · read
  verification-witness/SKILL.md · 3 observers drafted"). The emit channel
  already streams per-tool-call events (built for the stall detector); the
  watcher already edits a progress message. This is *wiring two existing seams*,
  not new machinery.
  **Gate:** live dogfood topic shows ≥3 progress edits during authoring; e2e
  pins the edit cadence and the settle-on-complete behavior.
- **V1.2 Author-model override.** Config key `:goal/author-model` — authoring on
  a fast non-reasoning model, turns keep the reasoning model. Provider probe
  evidence: non-reasoning answers in seconds vs ~60s rounds.
  **Gate:** golden authoring fixture — same spec authored by both models, output
  passes the same schema validation; latency delta measured and recorded in the
  commit message. Quality regression = we don't ship the override, we ship the
  measurement.
- **V1.3 Author-round instrumentation.** The evidence collector gains
  rounds/tokens-per-phase so V1.2's measurement is a command, not a vibe.
  **Gate:** collector output includes `authoring: N rounds, T tokens, M minutes`.

## V2 — Artifacts out

Goals build files; the topic gets a paragraph. On fulfillment the watcher
delivers the primary artifact via sendDocument (report HTML, witness MD, or
workspace tarball when configured). Parity roadmap listed outbound documents as
P2 — this is the goal-loop half of it.
**Gate:** dogfood goal delivers its `report.html` as a Telegram document to the
owning topic; e2e with a fake Bot API pins the multipart send.

## V3 — Goal ops from chat

`/goal list`, `/goal status`, `/goal cancel` (kill runner + announce honestly),
alongside existing resume. All read from the registry/ledgers that already
exist — the read paths were split into `goal/registry` + `goal/progress` in R2
precisely so this is consumption, not surgery.
**Gate:** one e2e per command; cancel proven to kill the runner pid and leave
the workspace resumable.

## V4 — Skill economy: measure, then prune

The contract ("read SKILL.md before claiming, cite `:skills-used`") shipped in
v0.9.0 but nothing measures compliance across runs. Extend `bb stats` with a
per-skill ledger: path-ref reads vs bare mentions, per goal, over time — the
evidence collector already computes this for one run; lift it to the home
level. Graduate skills that earn reads; prune skills that are pure decoration.
**Gate:** `bb stats` shows per-skill usage across ≥3 runs; one dogfood where an
additional skill is load-bearing *or* a deliberate prune commit with the
evidence cited. Wilson lower bound for the graduate/prune call, per the
skill-trust convention.

## V5 — Multi-goal scheduling

Parallel goals across topics are proven (dogfood, ledger-verified). Same-topic
is bounce-only and there is no global cap. Add a per-topic queue (second goal
queues, starts on the first's verdict) and `:goal/max-concurrent` global cap.
**Gate:** two goals in one topic — second queues visibly, starts automatically;
cap enforced across topics.

## V6 — Release automation

`bb release <version>`: asserts the CHANGELOG section exists, runs the full
gate, tags, pushes — with explicit owner approval before the push. This week I
hand-moved a tag; humans should not do git surgery by hand at the end of every
cycle.
**Gate:** v1.0.0 is cut *by it*.

## V7 — Human-shaped observability

- **Daily digest cron:** yesterday's usage, outbox depth, goal verdicts, stalls
  — one message to the owner's DM through the durable outbox. Not a dashboard.
  **Gate:** digest content matches `bb stats` for the same window.
- **Paper cut (found today):** `bb stats` silently reads the default home when
  `OPENCRABS_HOME` is unset — I audited a graveyard and filed a phantom bug.
  Print the home it's reading as line one. One line, ship immediately.

---

## Refusals (the spine)

- No dashboard, no metrics stack, no Grafana. Ledgers + `bb stats` + digest.
- No plugin/workflow engine. Goals compose via files and topics.
- No multi-tenant abstraction. One owner, explicit operator list.
- No new storage engine. EDN files and the existing outbox/registry pattern.
- No streaming edit-in-place for turns (parity doc already refused; still right).
- No author-prompt "optimization" without V1.3 measurement first.

## Ordering

V1 → V2 → V3 → V4 → V5 → V7 → V6. V1 first because silence is the worst UX and
its seams already exist; V6 last because it cuts the release that closes the
cycle. Each item is independently shippable with its own gate.

## Hickey note

Every item here *exposes what the system already knows*: progress events exist,
artifacts exist, registries exist, ledgers exist. v1.0 is composition of
existing seams — the diff should read as wiring, not machinery. If any item
starts growing a framework, that's the signal it's being built wrong.
